# 추천 작업 조회의 가수 ID 보존

기준: develop `a884912ca24377f0689563304699dd3a4f597a95`.
작업 브랜치: `codex/recommend-artist-id-preservation`.

## 원인과 변경

`GET /recommendations/{jobId}`는 반복 폴링 때 카탈로그를 재로드하지 않도록
`public_response(job)`을 호출한다. 기존 변환 함수는 매핑이 없으면 이미 저장된
`artist_ids`도 무조건 `[]`로 덮었다. 저장 원본이 아니라 조회 응답에서 ID가 소실됐다.

- 기존의 비어 있지 않은 양의 BIGINT 정수 ID 목록은 그대로 복사해 반환한다.
  숫자 문자열·boolean·0·음수·BIGINT 범위 밖 값은 정상 ID로 간주하지 않는다.
- 검증된 과거 ID는 현재 카탈로그가 다른 ID를 가리켜도 바꾸지 않는다.
  선반별 항목과 이전 호환용 recommendations 항목에 동일하게 적용한다.
- ID가 없는 복구 작업은 서버 시작 시 보강한다. 해당 작업이 있는 경우에만
  한 번 `CatalogIndex.load(..., verify_hashes=True)`와 가수 스냅샷 검증을 실행해
  여러 작업에 재사용한다. 추론이나 BE 요청은 수행하지 않는다.
- 정확한 track_id 또는 문자열 canonical song_id로만 보강한다.
  곡 이름·가수 이름·TJ 번호·숫자 song_id를 곡 식별자로 추측하지 않는다.
  알 수 없는 곡은 빈 ID 목록을 유지한다.
- 수정된 job.json을 원자적으로 저장한 뒤 메모리 결과를 교체한다.
  파일 교체 실패 시 원본 파일과 메모리 결과를 유지하며 서버 시작은 계속된다.
- 점수·추천 순서·키·상태·시간 기록·비공개 요청/콜백 자료는 보존한다.
  조회 응답에서는 기존처럼 비공개 입력/콜백 본문을 제외한다.
- GET 폴링에서는 카탈로그 로드·설정 읽기·job 저장을 하지 않는다.

새 점수식, 70/15/15 가중치, APK, BE DB 스키마는 변경하지 않는다.

## 적용과 확인

1. 변경 반영 후 AI 추천 서버를 정상 실행 환경에서 재시작한다.
2. 재시작 전 job 저장 디렉터리를 백업한다. 기존 job 중 ID가 없었던 결과의
   메타데이터를 보강해 저장하므로 백업은 비교와 복구에 유용하다.
3. 과거 작업 보강에는 현재 모델 계약과 일치하는 검증된 v3 카탈로그 및
   `artist_ids.json`이 필요하다. 저장소의 기본 v2 카탈로그를 문자열만 바꾸거나
   검증을 우회하지 않는다.
4. 기존 ID가 있는 job의 GET에서 `artist_ids`가 유지되는지 확인한다.
   ID가 없던 작업은 정확한 곡 식별자에 대해 보강되었는지 확인한다.
   반복 GET에서 점수·순서·키가 달라지지 않는지도 확인한다.
5. 이미 BE에 저장된 추천을 다시 계산하거나 DB를 자동 보정하는 변경은 아니다.
   운영의 앱→BE→AI 결과 확인은 지정한 테스트 계정에서 별도로 진행한다.

로그:

- `recommendation_artist_ids_repaired jobs=N`: 저장까지 성공한 작업 수.
- `recommendation_artist_ids_repair_unavailable error_type=...`: 설정·카탈로그·스냅샷 문제로
  과거 작업 보강을 생략. 서버 기동은 계속되며 기존의 정상 ID 보존은 작동한다.
- `recommendation_artist_ids_repair_save_failed job_id=... error_type=...`: 해당 job 파일의
  원자적 저장 실패. 원본은 유지되고 다음 재시작 때 다시 시도할 수 있다.

## 검증

관련 AI 테스트 139개 통과. 기존에 실패하던 과거 추천 GET 검사도 통과했다.
정적 계약·배포 검사 79개도 통과했다(카탈로그 링크 7개는 AI 검사와 중복).
Python 컴파일 검사와 `git diff --check`도 통과했다.
여기에는 다음 검사가 포함된다:

- 정상·잘못된 ID 구조, 선반별/중첩 ID, 다른 버전 카탈로그에서 과거 ID 보존.
- 복구 작업 여러 개에 카탈로그를 한 번만 로드하고 job 파일 저장·재복구.
- 동시 GET 32회 및 실제 FastAPI HTTP GET에서 ID 보존과 비공개 본문 차단.
- 이미 정상인 작업이나 결과 없는 작업에서는 카탈로그를 로드하지 않음.
- 스냅샷 hash 불일치·카탈로그 실패·파일 교체 실패 시 원본 보존.
- 카탈로그 로드 중 작업 결과가 갱신돼도 새 결과를 덮어쓰지 않음.
- 앱 시작 경로에서 보강을 한 번 실행하고 조회에는 넣지 않음.
- 추천 가중치·음역 소프트 점수·선반 구성·큐·콜백 회귀.

기존 두 항목은 이번 실행에서 제외했다: 기본 카탈로그의 v2/v3 버전 불일치 검사와
로컬 오디오 전처리 의존성 로딩이 지연되는 검사. 이를 해결됐거나 통과했다고
판단하지 않는다. 운영 서버·실제 사용자 DB 호출이나 배포는 하지 않았다.

## AI 담당자 전달 문구

추천 상태 조회에서 저장된 artist_ids가 빈 배열로 변환되던 오류를 수정했습니다.
정상적으로 저장된 ID는 보존하고, ID가 없는 과거 job은 서버 시작 시 검증된
카탈로그와 가수 스냅샷으로 정확한 track_id/song_id만 보강해 저장합니다.
반복 폴링 시 카탈로그 재로드는 추가하지 않았습니다. 변경 반영 후 추천 서버를
재시작하고, 기존 job의 GET 결과에 가수 ID가 남는지 확인해 주세요.
과거 job 보강에는 실제 v3 카탈로그가 필요하며, 보강 실패 시 원본은 유지하고
기동은 계속됩니다. 새 APK나 BE 스키마 변경은 필요하지 않습니다.
