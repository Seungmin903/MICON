# 추천 발성 점수 적용 및 배포 인계

기준 develop: `e6be37e8`. 작업 브랜치: `codex/recommend-continuous-stability`.
추천 변경만 포함한 독립 MR이다. 음역측정 실험은 별도 `codex/voice-quality-continuous-v2` MR이며,
이 MR을 적용해도 앱의 기존 v1 발성 점수식은 변경되지 않는다.

## 확정 정책

- 음성 유사곡: ECAPA 70% + Singer-BYOL 15% + 발성 적합도 최대 15%.
- 음역 밖 시간 5%, 곡 음역 데이터 누락, 음역 프로필 신뢰도로 음성 유사곡 후보를 탈락시키지 않는다.
- 음색 점수 내부 모델 비중은 70/85 : 15/85이다. 이를 85%에 반영해야 최종 70/15/15가 된다.
- 발성 적합도는 원본 `voiceQuality.points[].midi/score`와 곡의 지속시간 가중 음정 분포로 계산한다.
- 측정된 0점과 측정되지 않은 음을 구분한다. 미측정 음은 0점·연결선 보간값으로 만들지 않는다.
- 발성 비중 = `0.15 × measuredCoverage × catalogConfidence`. 부족한 비중은 음색 70:15로 재정규화한다.
- 원키부터 ±3키까지 비교하며 동점이면 측정 신뢰도, 원키와 가까운 키를 우선한다.
- 원키 선반은 기존 원키 커버리지·곡 음역 신뢰도 조건을 유지한다.
- 선반 내부 곡 중복 금지, 선반 간 중복 허용. 새로운 발견은 다른 선반에 없는 곡을 우선한다.
- 모든 선반에서 동일 표시 가수 최대 3곡. Android는 선반별 최대 15곡을 표시한다.
- AI/BE는 선반별 최대 50곡을 보관한다. 새로운 발견은 이 후보 안에서 다시 섞고 화면에서 15곡/가수당 3곡을 적용한다.
- 선택하지 않은 알려진 DB 장르는 기존대로 제외한다. 원천 후보가 적으면 15곡을 보장하지 않는다.

## 계약과 저장

- BE→AI: `voiceProfile.voiceQuality`에 저장된 원본 `{version, referenceMidi, points}`를 추가한다. 구형 데이터의 null은 허용한다.
- 후속 연속 발성 점수 변경으로 AI는 `personal-acoustic-v1`과 `personal-acoustic-v2`를 모두 읽는다. 점수는 전달된 원본을 그대로 사용한다. v2 실험 Debug APK 적용 전에 BE/AI 수용 변경을 먼저 배포한다. v2는 기준음 민감도 검증이 남아 기본 Debug/Release에서 꺼져 있다.
- 추천 점수 버전: `voice-stability-70-15-15-v1`.
- 추천 선반 버전: `shelves-v6-stability-soft-score`.
- 발성 상세 버전: `measured-stability-v1`. 곡의 음역 경계와 측정 발성 자료가 독립적이므로 일부 기존 음역 상세 항목은 null이 될 수 있다.
- `metrics.stability`에 점수, `measuredCoverage`, confidence가, `metrics.effectiveWeights`에 실제 반영 비중이 들어간다.
- 모델/닮은 가수 검색 계약 `ecapa-singer-byol-absolute-fusion-v3`은 유지한다. 추천 정책 변경 때문에 ARTIST_SEARCH 요청 버전을 바꾸지 않는다.
- V45는 기존 행을 삭제하지 않고 추천 곡 기본키를 `(recommendation_id, recommendation_shelf_id, song_id)`로 변경한다.
- 단일 곡 상세 조회 및 곡 적합도는 같은 곡이 여러 선반에 있으면 가장 앞의 overall_rank 행을 사용한다.

## 적용 순서

1. BE를 먼저 배포해 V45와 발성 점수 전달·선반별 중복 검증을 적용한다. 구형 AI 결과도 저장할 수 있다.
2. AI 담당자가 동일 병합 커밋을 받아 추천 서버를 재시작한다. worker 1과 기존 동시 실행·대기 제한은 유지한다.
3. AI 원본 job에서 추천/선반 버전, 발성 점수와 실제 가중치, 선반별 반환 수, 가수당 3곡을 확인한다.
4. 양쪽 반영을 확인한 뒤 BE 런타임에 `AI_RECOMMENDATION_REQUIRED_SHELVES_VERSION=shelves-v6-stability-soft-score`를 설정하고 재시작한다. 이후 앱 방문 시 구형 완료/빈 추천의 latest가 404를 반환하여 앱이 새 추천을 요청한다. 기존 결과는 삭제하지 않으며 ID 조회로 남는다. 생성 중인 작업은 버전 때문에 숨기지 않는다.
5. Android 변경이 들어간 새 APK를 배포해야 15곡 표시 및 화면의 가수당 3곡 제한이 적용된다. 기존 APK는 최대 30곡 표시 로직을 유지한다.
6. 지정한 테스트 계정에서 새 추천을 만들어 AI→BE→앱의 곡 수와 순서를 비교한다. 실제 사용자 추천 생성은 BE에 쓰기 작업이므로 담당자가 승인된 계정으로 수행한다.

구형 사용자에게 음별 발성 점수가 없으면 음색 중심으로 정상 완료한다. 재측정 전까지 없는 발성 점수를 생성하지 않는다.

## 검증 결과와 범위

- MR 단독 작업 사본에서 AI 관련 95개, BE 관련 76개, Android 전체 JVM 테스트 525개 통과.
  Android의 별도 진단 녹음 재생 3개는 입력 파일 미제공으로 생략했다(총 528개 중 525개 통과/3개 생략).
  GitLab 정적 계약과 카탈로그 링크 검사 79개도 통과했으며 카탈로그 링크 7개는 AI 95개와 중복이다.
- CI 검사에서 새 `AI_RECOMMENDATION_REQUIRED_SHELVES_VERSION` 환경변수 예시/운영 계약 누락을 발견해
  backend와 Compose 예시에 빈 값으로 추가하고 런타임 계약 문서에 적용 순서를 기록했다.
- 합성 임베딩 ECAPA 0.8 / Singer-BYOL 0.4 / 발성 0.6을 실제 추천 계산과 공개 응답 스키마에 통과시켜 최종 0.71을 확인했다. 실제 모델 추론이나 운영 추천 성능 측정은 아니다.
- 결측 발성 자료, 측정된 0점, 음역 밖 곡 유지, 재생 가능 키 범위, 선반 간 같은 곡 저장·조회, 15곡 표시와 가수당 3곡 제한을 검증했다.
- BE 마이그레이션·저장 통합 테스트는 H2 기반이다. 로컬 Docker가 준비되지 않아 실제 MySQL 마이그레이션은 실행하지 않았다. 운영 반영 전 별도 MySQL 검증과 DB 백업이 필요하다.
- 로컬 보존 카탈로그의 `index.json.scoring_version`은 v2이며 현재 모델 계약은 v3이다. 버전 검사를 우회하거나 카탈로그 버전 문자열만 바꾸지 않았다. 운영 담당자가 사용 중인 v3 카탈로그를 확인해야 한다.
- 이 때문에 실제 곡 기반 응답 샘플 재생성은 완료하지 못했다. `scripts/make_sample_response.py --schema-only`로 현재 응답 스키마만 갱신했으며, 기존 sample-response 파일은 이전 예제다. v3 카탈로그 확보 뒤 `--index-dir <v3 catalog> --quality-score 85`로 합성 발성 샘플을 재생성할 수 있다.
- Python JSON/추천 단위 검증에만 `NUMBA_DISABLE_JIT=1`을 사용했다. 운영 실행 설정이나 모델 가중치는 바꾸지 않았다. 오디오 전처리 회귀 테스트 한 건은 로컬 의존성 로딩이 지연돼 검증 목록에서 제외했다.
- 운영 서버 호출·실제 사용자 추천 생성·배포는 하지 않았다. 검토용 MR로 제출하며 직접 병합/배포하지 않는다.

## AI 담당자 전달 문구

추천 방식을 ECAPA 70% / Singer-BYOL 15% / 음별 발성 적합도 최대 15%로 변경했습니다. 음성 유사곡의 음역 탈락 필터를 제거하고, BE가 전달하는 personal-acoustic-v1 원본 음별 점수를 곡의 지속시간 가중 음정 분포에 반영합니다. 미측정 음은 0점 처리하지 않고 발성 가중치를 줄이며, 자료가 없으면 음색만으로 추천합니다. 모든 선반은 가수당 최대 3곡이고 선반 간 같은 곡을 허용합니다. BE의 V45와 콜백 저장 정책 변경을 먼저 배포한 뒤 같은 병합 커밋으로 AI 서버를 재시작해 주세요. 추천 버전은 voice-stability-70-15-15-v1 / shelves-v6-stability-soft-score이며 ARTIST_SEARCH 모델 계약 v3은 유지합니다. 운영 적용 후 원본 job의 실제 가중치와 선반별 곡 수를 확인 부탁드립니다.
