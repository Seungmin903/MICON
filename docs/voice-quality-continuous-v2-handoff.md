# 연속 발성 점수 v2 — 개인 녹음 기반 탐색적 개선

## 목표와 범위

진성/가성 분류 모델을 만드는 것이 아니다. 발성의 음향 변화에 따라 자연스러운 중간값이
존재하는 0~100 연속 점수를 만든다. 충분히 유지된 진성 쪽 특성은 100, 완전 가성 쪽
특성은 30을 기준점으로 사용한다. 중간 발성의 목표 점수를 파일 라벨로 강제하지 않는다.
끊김·유지 실패가 있으면 30 미만도 가능하다. 좋은/나쁜 목소리, 건강, 성대 폐쇄율,
가성 확률이나 의학적 진단 점수가 아니다.

실제 구현 위치는 Android `LocalVoiceQualityAnalyzer`이다. 음정을 추적하는 YIN,
AI 서버의 CREPE/pYIN, ECAPA/Singer-BYOL 모델 가중치는 변경하지 않았다.
이 MR의 AI 디렉터리 변경은 오프라인 비교 도구뿐이다.
추천 AI의 새 `voiceQuality` 버전 수용은 별도 `codex/recommend-continuous-stability` MR에 포함한다.
음역측정 MR은 `codex/voice-quality-continuous-v2`이며 동일 develop `e6be37e8`에서 독립적으로 시작한다.

사용자는 녹음 7개가 동일 화자·기기·비슷한 거리·무반주라고 확인했고, 음량은 다를 수 있다고 했다.
원본 7개 모두 FFmpeg에서 AAC-LC, 44.1kHz, mono, 128kbps로 확인했다.

## 확인한 기존 문제

- v1 기준음은 스스로 비교하므로 점수가 자동으로 100에 가까워진다.
- 기준음 이하에는 고음 변화 벌점이 없어 같은 높이의 얇은 발성을 놓칠 수 있다.
- 가성도 주기성이 높을 수 있다. 이번 완전 가성의 주기성 중앙값은 약 0.98이었다.
- H1/H2 중앙값은 이번 가성에서 약 -0.2~0.5dB였다. H1/H2 상승만으로 구분할 수 없다.
- 반면 고차 배음 비율과 H2/H4에서는 이번 녹음의 연속적인 차이가 나타났다.
- 약한 추적 신뢰도의 프레임도 음향 증거 집계에 섞일 수 있어 유성 프레임 조건을 적용했다.

## 계산식

`R`은 H3~H6 에너지/H1~H2 에너지의 dB 비율이고, `H`는 H2/H4 진폭의 dB 비율이다.
둘 다 절대 음량이 아닌 비율이다. 주기성은 정규화 상관이다. 단순히 높은 음이거나
조용하다는 이유로 가성 쪽 점수를 주지 않는다.

```text
r = clamp((R_reference - R_observed - 2) / 12, 0, 1)
h = clamp((H_observed - H_reference - 2) / 14, 0, 1)
relative = 0.5 × (0.6r + 0.4h) + 0.5 × sqrt(rh)

a = clamp((-2 - R_observed) / 5, 0, 1)
b = clamp((H_observed - 4) / 6, 0, 1)
registerChange = max(relative, sqrt(ab))

score = clamp(100 - 70 × registerChange - 75 × lowIrregularity, 0, 100)
        × (0.65 + 0.35 × holdScore / 100)
```

범주 판정, 임계값을 넘으면 30/100으로 강제하는 분기, 파일명 기반 점수 할당은 없다.
두 배음 지표를 부드럽게 결합하여 한 지표만 바뀌면 부분적으로 반영한다.
절대 음향 가드는 기준음 자체가 얇게 발성된 경우 자동 100점이 되지 않게 한다.
단, 위 수치는 이 화자의 녹음으로 탐색한 휴리스틱이며, 보편적인 성구 경계로 검증된 값은 아니다.

무음·비정상 수치 파형은 점수를 만들어 내지 않는다. 미측정 반음은 계속 결측으로 남긴다.
짧게 끊긴 추적 음은 기존처럼 유지 실패 0점으로 기록할 수 있다.

## 실제 녹음 비교

Android의 실제 `evidence/registerChange/score` 코드를 JVM에서 실행했다.
원본을 16kHz PCM으로 디코딩하고 별도 YIN 진단 추적으로 프레임을 만든 뒤,
`진성.m4a`의 중앙 음향 증거를 기준으로 비교했다. **유지점수 100을 가정한 음향 성분
비교이며, 앱에서 완전한 온보딩을 다시 수행한 최종 그래프 점수는 아니다.**

| 파일 | v1 비교 점수 | v2 비교 점수 |
|---|---:|---:|
| 진성 | 100.0 | 100.0 |
| 진성-1 | 100.0 | 100.0 |
| 솔 진성 | 100.0 | 100.0 |
| 가성 | 62.5 | 30.0 |
| 가성-1 | 62.5 | 30.0 |
| 솔 조금 가성 | 71.9 | 73.5 |
| 너무낮아서 끊기는 음 | 57.5 | 57.1 |

저음 파일은 활성 구간 약 7.26초 중 신뢰도 기준을 통과한 추적 구간이 약 0.5초였다.
최종 온보딩에서는 유지 실패가 추가로 반영되거나 점을 확정하지 못할 수 있다.
이 57.1점을 실제 유지 가능한 최저음의 평가로 해석하면 안 된다.

원본 파형을 -12dB로 디지털 감쇠한 음향 성분 비교에서는 동일 점수를 얻었다.
감쇠 시 신호·배경음이 함께 줄고 피치 추적은 원래의 진단 추적을 재사용했다.
실제로 작게 발성하여 SNR·음색이 바뀌거나, 다른 AGC/노이즈 제거를 거친 상황을 검증한 것은 아니다.
소리가 배경 잡음 수준이면 점수 대신 측정 불충분 처리가 필요하다.

연속 변화 테스트에서는 점진적인 배음 변화가 100~30 사이의 여러 서로 다른 중간값을
만드는지 확인했다. 3개 진성 기준에 대한 민감도도 별도 TSV로 남겼다.

**출시 보류 근거:** 같은 `솔 조금 가성`의 음향 성분 점수가 기준 녹음에 따라
73.5(`진성`), 61.5(`진성-1`), 42.0(`솔 진성`)으로 달라졌다.
진성 파일들도 기준에 따라 83.4~100점이었다. 완전 가성 두 파일은 세 기준에서 모두 30점이었다.
연속성을 확인한 것과 기준음·화자에 대해 점수가 잘 보정되었다는 것은 별개다.
이 민감도를 숨기거나 같은 7개 파일을 더 맞추기 위해 가중치를 재조정하지 않는다.
같은 음높이·모음의 반복/중간 발성 녹음과 별도 세션으로 기준점 보정,
여러 기준음의 통합 또는 음높이별 기준, 포먼트 영향을 먼저 검증해야 한다.

## 검증 한계 / 다음 실험

- 1명, 7개 파일의 탐색·조정·동일 데이터 재평가다. 독립 테스트셋 성능이나 분류 정확도를 주장하지 않는다.
- 완전 진성/가성 녹음은 음높이도 달라, 음높이와 모음·포먼트의 영향이 섞인다.
  같은 높이의 진성/중간/가성을 반복 녹음하고 모음을 고정한 검증이 필요하다.
- H2/H4와 배음 비율은 포먼트 보정을 하지 않은 음향 대리 지표다. 모음·공명·입 모양·마이크 응답의 영향을 받는다.
- 44.1kHz·AAC 128kbps는 이번 탐색 실험에는 사용 가능했으나, 압축 전 WAV와의 짝 비교가 없으므로
  압축이 무영향이라거나 정밀 지표에 충분하다고 보장하지 않는다.
- 추가 녹음은 동일 기기·거리, 반주 없음, WAV PCM 16bit/44.1 또는 48kHz로 받는다.
  같은 음/모음에서 진성~중간~가성을 여러 강도로 반복하고, 다른 날짜·화자·기기의 별도 평가 데이터를 확보한다.
- 평가는 파일/세션/화자 단위로 분리한다. 한 파일의 창을 학습·검증 양쪽에 섞지 않는다.
- 출시 전 실제 기기 온보딩, 원래 44.1/48kHz 입력, AGC·배경 잡음·재시도 상황을 추가 검증한다.

근거: [음성 압축과 음향 분석 연구](https://pmc.ncbi.nlm.nih.gov/articles/PMC2945273/),
[성구의 연속적 음향·지각 특성 연구](https://www.isca-archive.org/speechprosody_2008/salomao08_speechprosody.pdf).
이 문헌이 본 점수식의 수치나 모든 AAC 128kbps 파일의 정확성을 보증하는 것은 아니다.

## 로컬 검증 결과

- 음역측정 MR 단독 작업 사본에서 Android 전체 JVM 테스트 530개, BE 점수/세션 관련 14개,
  GitLab 정적 계약/카탈로그 링크 79개 통과. 전체 저장소 통합 테스트나 운영 정확도 검증은 아니다.
- Android는 실험 Debug 설정을 켜고 실행했으며, 비공개 녹음 비교 테스트 1개도 실제 실행했다.
  별도 진단 녹음 재생 3개는 해당 입력 미제공으로 생략했다(총 533개 중 530개 통과/3개 생략).
  기본 분석 호출은 v1을 생성하고 명시적 실험 호출만 v2를 생성하는지 함께 검사했다.
- Python 컴파일 검사, `git diff --check` 통과. 원본 7개 SHA-256은 모두 변경 전과 같다.
- Release BuildConfig 생성 시도는 기존 Release 서명정보 필수 검사에서 중단됐다.
  서명 검증을 우회하지 않았고 Release APK는 만들지 않았다. Release 실험 설정은 소스에서 false로 고정한다.
- 실제 모바일 마이크 온보딩, 운영 BE/AI 왕복, 다른 화자에 대한 정확도는 검증하지 않았다.

## 계약 / 적용 순서

- 기존 `personal-acoustic-v1`을 계속 허용하며 기존 점수는 재계산하지 않는다.
- 실험용 새 결과는 `personal-acoustic-v2`. `points[].registerChange`는 필수 0~1 값이다.
- 기본 Debug와 모든 Release는 아직 v1을 생성한다. Debug에서만
  `EXPERIMENTAL_CONTINUOUS_VOICE_QUALITY=true`를 환경변수 또는 local.properties로 명시해 v2를 켠다.
  Release는 환경변수와 관계없이 false로 고정한다. 검증 후 별도 변경으로 출시 활성화를 결정한다.
- BE는 v2 점수식을 검사한다. v1과 v2 모두 기존 80점 음역 표시 규칙에 사용한다.
- AI 추천은 v1/v2의 원본 `midi/score`를 읽는다. 모델/ARTIST_SEARCH v3 계약은 바꾸지 않는다.
- 순서: BE의 v1/v2 수용 배포 → AI의 v1/v2 수용 배포 → 실험 Debug APK → 지정 계정의 실제 온보딩 확인.
- 추천에 v2 점수를 반영하는 실험은 별도 추천 MR의 BE 전달/AI 수용 반영까지 확인한 뒤 진행한다.
  이 MR만 반영한 일반 앱은 기존 v1 계산을 유지한다.
- 그래프 레이아웃은 유지한다. 상세 진단 문구만 v2에서 ‘발성 변화 지표’로 표시한다.
- 이 변경을 시험하려면 v2를 켠 새 Debug APK가 필요하다. AI 서버 재시작만으로 앱 점수식은 바뀌지 않는다.

원본 녹음은 수정하지 않았고 외부 서비스에 업로드하지 않았다. 디코딩된 PCM·프레임·상세 보고서는
Git에서 제외되는 `ai/recommend-server/workspace/voice-calibration`에만 있다.
비공개 실험은 `MICON_VOICE_CALIBRATION_DIR`을 설정해 `VoiceCalibrationRecordingTest`로 재실행한다.
코드·인계 문서는 검토용 MR로 제출하며 직접 병합/배포하지 않는다.
